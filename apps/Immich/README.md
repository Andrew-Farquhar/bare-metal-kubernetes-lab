# Immich Deployment

## Overview

Immich is a self-hosted photo and video management platform. I sought to deploy this into the existing Kubernetes homelab rather than continuing to rely on externally hosted photo management services (iCloud at the time of deployment).

The deployment was an opportunity to experience deploying an application that required a suite of components to operate, with one important component being a Postgres Database instance. This allowed for some exploration of the CloudNativePG tool. 

The deployment also makes use of pre-existing infrastructure in the way of Longhorn to back stateful pods and the NAS for bulk storage. 

The aim was to keep the deployment as straightforward as possible.

## Architecture

| Component | Purpose | Storage / connectivity |
|---|---|---|
| Immich Server | Main application, API and web interface | NAS-backed NFS PVC; Service port 2283 |
| Machine Learning | Smart Search, facial recognition and other ML tasks | Longhorn PVC for model cache |
| Valkey | Cache and background job coordination | Deployed as an Immich chart dependency |
| PostgreSQL | Stores Immich application metadata | CNPG-managed instance; Longhorn PVC |
| CloudNativePG | Manages the PostgreSQL cluster and database resources | Kubernetes operator in `cnpg-system` |
| Traefik | Provides external access to Immich | Existing Gateway and HTTPRoute |
| NAS | Stores the managed photo and video library | ZFS-backed storage, exposed over NFS |

## Configuration Decisions

## Application storage

Decision: Store Immich's managed media on the NAS using NFS, rather than longhorn storage on the cluster

The NAS already provides ZFS-Backed storage exposed to the cluster via NFS. There's considerably more capacity than is present on the nodes themselves and with some media being irreplaceable this gives peace of mind that a drive failure or fault will not result in total loss (although Longhorn has it's own redundancy in place also).

Immich reuses the same persistentVolume and persistentVolumeClaim as the plex deployment, however, different paths are exposed to each deployment. 

## PostgreSQL

Decision: Use CloudNativePG (CNPG) to manage PostgreSQL separately from the Immich Helm deployment. 

The database runs as a single-instance CNPG cluster, with it's persistent volume provisioned via Longhorn.

This separation keeps the DB's lifecycle management away from the application chart.

Database Configuration:

- PostgreSQL 18

- CloudNativePG operator 1.30.1

- CloudNativePG Helm chart 0.29.1

- Longhorn persistent storage

- VectorChord and pgvector extensions

## Resilience

The approach taken was to use a single database instance and single application instance rather than introducing additional overhead to make the application High Availability. For a self-hosted application the key component to protect was the data itself, which is covered as best as possible with a ZFS managed storage pool. Unfortunately in a bare-metal cluster of slightly aged USFF nodes running multiple instances/pods for HA purposes may well lead to resource pressure and introduce the risk of incidents and impact rather than reducing it.

## Database Backups

Immich creates it's own Database backups with a user defined retention policy. Immich stores these backups in the same PV that the media is stored on. For additional redundancy these are being exported to a second pool on the NAS via a daily cronjob. 

## Deployment

# 1. Install CloudNativePG

The CNPG operator was installed using Helm. 

- Chart: cloudnative-pg/cloudnative-pg
- Chart version: 0.29.1
- Namespace: cnpg-system

The operator is managing the PostgreSQL resources via Kubernetes custom resource definitions. No custom values were required when installing the chart at all. 

# 2. Provision PostgreSQL

Two resources were created:

- Cluster: provisions and manages the PostgreSQL instance
- Database: created the Immich database and configures the required extensions.

The created DB has credentials managed via a Kubernetes Secret generated by CNPG.

# 3. Provision media storage

A dedicated NFS-backed PV and PVC were created:

PV: nas-immich-pv

PVC: nas-immich-pvc

Capacity: 10Ti

Access mode: ReadWriteMany

Reclaim policy: Retain

The NAS export is mounted from the Immich-specific directory rather than the root media export.

# 4. Deploy Immich

Immich was installed using the official Helm chart.

- Chart: Immich
- Chart version: 0.13.4
- Application version v3.2.0
- namespace: apps

Custom values were passed in to ensure resource requests, limits and PV/PVCs were provided to the Chart when deploying. The Immich server, machine-learning and Valkey dependency were all deployed using the chart simultaneously.

# 5. Configure ingress

An HTTPRoute was created to attach Immich to the existing Traefik Gateway.

The route forwards requests for immich.home to the immich-server Service on port 2283.

No separate ingress controller or LoadBalancer service was required.

## Troubleshooting and Lessons Learned

# NFS permissions and root squashing

The initial deployment failed because Immich could not create directories under its mounted storage path.

The NAS media export uses root_squash, meaning root on the Kubernetes nodes is mapped to an unprivileged identity on the NAS.

The solution was to configure the Immich server pod security context to match the ownership of the NAS directory:

runAsUser: 1000

runAsGroup: 1001

fsGroup: 1001

This allowed Immich to write to the NAS without weakening the existing NFS export security.

# Correcting the NFS mount path

The initial PV pointed at the root media export rather than the dedicated Immich directory.

As a result, Immich created its storage directories alongside existing media such as Plex's Movies and TV Shows directories.

The PV and PVC were recreated with the corrected NFS path:

/media/immich

The reclaim policy was set to Retain, preserving the underlying NAS data during the Kubernetes resource replacement.

# Immich storage marker files

After correcting the mount path, Immich entered CrashLoopBackOff because the new storage location did not contain its expected .immich marker files.

The six storage directories were created and initialised with their respective marker files.

Immich then passed its storage integrity checks and started successfully.

Lesson: When using a fresh NFS-backed storage location, account for Immich's expected directory structure and marker files.
