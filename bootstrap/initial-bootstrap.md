# Node Preparation

Note: File naming conventions in this document are not inline with the current YAML files in this repository. 

The following preparation was performed on each Kubernetes node.

* Debian 13 installed as a minimal headless system.
* System packages updated.
* Swap disabled.
* `containerd` installed from the Docker repository.
* `nerdctl` installed.
* `kubectl`, `kubeadm` and `kubelet` installed from the official Kubernetes v1.37 repository.
* Kubernetes packages held to prevent unintended version changes.

## Kubernetes Networking Prerequisites

`br_netfilter` was loaded and configured to persist across reboots. This allows bridged traffic to be processed by netfilter.

```bash
sudo modprobe br_netfilter
echo br_netfilter | sudo tee /etc/modules-load.d/kubernetes.conf
```

IPv4 forwarding was enabled and configured to persist across reboots.

```bash
sudo sysctl -w net.ipv4.ip_forward=1
```

The setting was persisted in `/etc/sysctl.d/kubernetes.conf`.

# Control Plane Bootstrap

The initial control plane was created on `node01` using a kubeadm configuration file.

The configuration defines:

* `node01`'s physical IP address as the advertised API endpoint.
* `192.168.1.240:6443` as the stable Kubernetes API endpoint. *Note that `:6443` later caused an incident during the final HA Build.
* `10.244.0.0/16` as the Pod network CIDR used by Flannel.
* The kube-apiserver binding address.
* The expected port conflict caused by HAProxy listening on the API VIP.

The cluster was initialised using:

```bash
sudo kubeadm init --config ~/kubeadm-config.yaml
```

## Configure kubectl

After `kubeadm init` completed, the generated administrator kubeconfig was copied to the `kube` user's home directory.

```bash
mkdir -p ~/.kube
sudo cp /etc/kubernetes/admin.conf ~/.kube/config
sudo chown kube:kube ~/.kube/config
```

`/etc/kubernetes/admin.conf` is generated by kubeadm and contains the information and credentials required for `kubectl` to authenticate with the cluster.

Copying it to `~/.kube/config` allows the `kube` user to use `kubectl` without specifying the configuration file manually.

## Install Flannel

Flannel was installed as the cluster CNI:

```bash
kubectl apply -f https://github.com/flannel-io/flannel/releases/latest/download/kube-flannel.yml
```

The control-plane node initially reported `NotReady`. Once Flannel was running, the node transitioned to `Ready`.

The Kubernetes system Pods were also checked to confirm that the cluster had successfully started.

# Result

`node01` was successfully established as the first control-plane node.

The remaining control-plane and worker nodes were subsequently joined to the cluster. This initial bootstrap was intended only to test creating a control-plane and joining nodes to it. The full HA bootstrap process is documented separately in `bootstrap-actual.md`.
